Tellurium Nitro

What changed from regular tellurium, how the new engine is built, and how to build it again yourself.
specJIT · plain-language edition · updated November 18, 2026

The one-paragraph version. Tellurium is a Python tool biologists use to simulate how the chemicals in a cell change over time. All the real number-crunching inside it is done by a C++ engine called roadrunner. Tellurium Nitro replaces that engine's work with a new engine written in the Rust programming language. The new engine solves the same equations, but it wastes far less work, it calculates exact answers where the old one used approximations, it uses every processor core, and it translates each model into native machine code (the "JIT"). It reads model files itself, so loading a big model no longer waits for roadrunner. Your Python code does not change: the same te.loada(), r.simulate() and r.steadyState() calls just come back faster. If the new engine ever meets something it can't handle, it quietly hands that job to the original engine. With that backup switched off, it passes every one of the 1,923 cases of the official SBML Test Suite on its own.

2. The problem being solved, in pictures

A biological model is a list of chemical reactions, for example "S1 turns into S2 at a speed of k1 × S1". Each reaction has a rate law (a small formula) and some parameters (numbers like k1). From those, the software builds a set of equations saying how fast each chemical's amount is changing. Then it answers questions:

  • Time course: start from some amounts and step forward in time to see how they change (like a movie).
  • Steady state: find the point where nothing changes any more (where the movie ends up).
  • Control analysis (MCA): if I nudge one reaction, how much does each chemical level or flow change? Biologists use this to find which enzymes really control a pathway.
  • Sensitivities: how much does the whole time course shift if I nudge each parameter?
  • Stochastic simulation: when there are only a few molecules, simulate random individual reaction events (the Gillespie method).
  • Flux balance (FBA): given only which reactions exist and their limits, what is the best possible set of flows (for example, the fastest growth)? This is a different kind of problem: a linear program, not a simulation.

Models can also contain rules (a value is always given by a formula), events ("when the concentration passes 5, add a dose"), delays ("the rate depends on what S1 was 2 seconds ago"), random numbers drawn inside the model, fast reactions (so fast they are always in balance) and algebraic constraints (equations that must always hold). All of these boil down to evaluating the rate-law formulas, and their slopes (derivatives), millions of times. How quickly and how cleverly you do that decides the speed.

3. Why regular tellurium is slow

We read roadrunner's source code and timed it. The slowness is not because C++ is slow; it comes from how the work is organised:

4. What Nitro does instead (the big ideas)

4.1 Exact slopes by algebra, not by trial. When the model is loaded, Nitro works out the derivative of every rate law symbolically, the way you would in a calculus class (the derivative of k1 × S1 with respect to S1 is k1). So "how steep is the hill" is answered with a formula, instantly and exactly, instead of 170,000 test steps. This is the single biggest reason steady-state and control analysis are thousands of times faster, and why Nitro's answers are more accurate.

4.2 Build once, reuse forever. The model is converted once and kept in memory. Later calls just plug in new numbers. Changing a parameter does not trigger a rebuild; only changing the model's structure (adding a reaction) does.

4.3 Control analysis in one shot. Control coefficients come from a known matrix formula, C = −L (NR E L)−1 NR and F = I + E C. Nitro computes the pieces once at the steady state and solves it in a single step.

4.4 Every core at once. The Rust engine has no shared global memory, so it runs thousands of parameter sets side by side on all CPU cores (with the Rust library rayon), without Python's one-thing-at-a-time lock (the GIL) getting in the way. This powers te.controlCoefficients, r.simulateBatch, sensitivities and the 10,000-run stochastic tests.

4.5 Native machine code (the JIT). The engine stores each formula as a "tape": a list of tiny instructions ("load k1, load S1, multiply..."), read one by one each time. That is like reading a recipe out loud step by step every time you cook. The JIT ("just-in-time compiler") translates the tape into the processor's own instructions with the Rust library Cranelift. It only does this after a formula has been used 2,000 times, so short one-off runs don't pay the compile cost. The compiled code gives bit-for-bit the same numbers as the tape.

4.6 Smarter time stepping. For time courses Nitro has two integrators (step-forward methods). At roadrunner's default accuracy and tighter (relative tolerance 1e-5 or below) it uses a variable-order BDF method, the same family as roadrunner's CVODE, with CVODE-style step-size and Newton control. At looser accuracy it uses Rodas4, which is faster there on small or event-heavy models. We chose the switch point by testing 10 models at 5 accuracy levels. Both reuse expensive work between steps and order their matrix math to avoid wasted work ("sparse LU with fill-reducing ordering"). If a run blows up, Nitro retries once with tighter accuracy.

4.7 Loading without roadrunner. Nitro reads the model file itself (with libsbml, the standard SBML reader), works out the starting values with its own formula evaluator, and builds its engine in a fraction of a second. Antimony text (the easy model language) is turned into SBML by a pure-Rust reader, about 4x faster than the original libantimony. Roadrunner is still installed, but it is only woken up ("lazy loading") the first time you ask for something Nitro does not do, such as editing the model's structure. It is then handed the current state, so results carry on seamlessly.

4.8 One traffic controller, and it never breaks your code. Every call goes through one decision point. It asks: can Rust do this exactly the way roadrunner would? If yes, Rust does it; if not, the call goes to roadrunner untouched. r.lastRun tells you which happened and why. te.turbo(False) switches the new engine off; te.turbo('strict') switches the backup off, so you can prove everything ran in Rust.

4.9 Models roadrunner refuses. Nitro handles delays, algebraic rules, fast reactions, multi-part ("comp") models and random numbers inside models ("distrib"). Section 7 explains how, feature by feature.

5. How it is built (architecture)

What happens when your code calls, for example, r.steadyState():

   | Steady state     | Time course      | Events, rules,   |

   | conservation laws| diffsol for DAEs | random draws     |
   +------------------+------------------+------------------+
   | Control analysis | Sensitivities    | Stochastic       |
   | one matrix solve | exact, one       | Gillespie,       |

   +------------------+------------------+------------------+

  • Your code calls tellurium as usual. Antimony text becomes SBML.
  • The bridge reads that SBML and builds the Rust model; roadrunner is not asked to compile it.
  • The Rust model holds every formula as a tape, its exact derivatives, the conservation laws (totals that never change, like free + bound enzyme), events, rules and delay histories. Hot tapes are compiled to machine code.
  • A Session object keeps the event state between simulate calls, counts solver steps, and retries a failed run with tighter accuracy.
  • The right solver runs. Batches fan out across all CPU cores.
  • Results come back in the same form as before, so plots, selections and getters keep working.

7. Every SBML feature, and how Nitro handles it

FeatureWhat it meansHow Nitro does it
Reactions, parameters, compartmentsThe basics.Each species' rate of change = sum of (stoichiometry × reaction rate), divided by compartment size for concentrations.
Assignment and rate rules"x is always this formula" / "x changes at this rate".Assignment rules are evaluated in dependency order before each rate evaluation; rate rules become extra equations.
Algebraic rules"this equation must always be 0".If the equation can be solved for one variable, the bridge turns it into an assignment rule. If not, the model is a DAE (differential-algebraic equation) and goes to the diffsol BDF solver, which first finds a consistent starting state.
Fast reactionsSo fast they are always in balance.Each fast reaction's "extent" is an unknown fixed by "its rate = 0"; each fast species = its slow-driven base amount + stoichiometry × extent. Works even when stoichiometry changes over time or an event switches the reaction off.
Events"When the trigger becomes true, change these values" (optionally after a delay, with a priority).Every comparison inside a trigger is watched, so a short trigger window is never stepped over. Delay, priority (ties broken at random, as SBML requires), persistence, "use values from trigger time" and "initial value = false" are all supported. Waiting events carry over between simulate calls.
delay(x, d)The value of x, d time units ago.The engine keeps a history of every state and looks up past values with smooth (Hermite) interpolation. Values before the start, nested delays and changing delays are handled; steps are kept shorter than the shortest delay. The history keeps both the value just before and just after an event.
comp (hierarchical models)Models built from sub-models.The bridge flattens them into one ordinary model with libsbml's flattening converter.
distrib (random numbers in formulas)e.g. normal(0, 1) inside a rate or event.Every evaluation draws a fresh number (never cached or simplified away). Each run has its own seeded random stream, so batches are reproducible.
Variable compartments, conversion factors, variable stoichiometry, function definitions, avogadro, rateOfLess common SBML features.All built into the equation builder. rateOf of a rule is differentiated with the chain rule.
Stochastic (Gillespie)Random individual reaction events.Standard SSA. If the model also has rate rules, a "hybrid SSA" integrates the rules and the total reaction propensity with RK4 and fires a reaction when the propensity integral reaches −ln(U), where U is a uniform random number.
Flux balance (fbc)Best flows under limits.te.fba: maximise or minimise the objective subject to N·v = 0 and the flux bounds, with SciPy HiGHS. An infeasible problem returns NaN.

8. Rebuild it yourself: a step-by-step recipe

This is the order we built Nitro in. Each step works on its own and is checked before the next starts. A programmer comfortable with Python and willing to learn some Rust can follow it.

Step 0. Tools

  • Python 3.9+ with regular tellurium and libroadrunner 2.10 installed (the reference to compare against).
  • Rust (rustup), and maturin to build Rust code as a Python module (pip install maturin).
  • Rust libraries: pyo3 and numpy (Python bindings), rayon (all cores), cranelift-* (JIT), diffsol (DAEs only).
  • Python: numpy, scipy (for FBA), python-libsbml.

Step 1. Measure before changing anything

Write a benchmark script (ours is benchmarks/run.py) that times steady state, control coefficients, simulate, sensitivities and loading on a few models, and records the error against a very-high-accuracy reference (roadrunner at relative tolerance 1e-12, absolute 1e-14). Read roadrunner's source to see why each slow call is slow (section 3). This tells you where the big wins are.

Step 2. Formulas as a tape, with exact derivatives

  1. Turn each rate-law formula (from libsbml's math tree) into a flat list of instructions: load a constant, load a variable, add, multiply, power, call a function, and so on. Evaluate it with a simple loop and a small stack.
  2. Write a function that takes a tape and a variable and returns a new tape for the derivative, using the normal calculus rules (sum rule, product rule, quotient rule, chain rule). Simplify as you go (0 × anything = 0).
  3. Pre-compute parts that only depend on fixed parameters, once.
  4. Check: every formula's value and derivative must match a numerical estimate to many digits on random inputs.

Step 3. Steady state and control analysis

  1. Build the stoichiometry matrix N (which reaction makes or uses which chemical). Find the conservation laws (rows of N that combine to zero) to get the link matrix L and reduced matrix NR.
  2. Steady state: Newton's method on the independent chemicals, using the exact Jacobian from step 2, with damped steps. If Newton fails, run the model forward in time to t = 1, 10, 100, ... up to 1,000,000 and try Newton again from each point, until it finds a valid answer (finite, no negative chemicals).
  3. Elasticities E come straight from the derivative tapes. Then C = −L (NR E L)−1 NR and F = I + E C. Scale by values and fluxes for the scaled versions.
  4. Check: match roadrunner's matrices. They will differ by about 1e-8 because roadrunner's slopes are approximate; tighten roadrunner's step size and the gap shrinks to about 1e-12, which proves the Rust answer is the exact one.

Step 4. Time courses

  1. Implement Rodas4 (a stiff Rosenbrock method) with error control, then a variable-order BDF with CVODE-style step-size and Newton control. Both solve linear systems with a sparse LU that reorders rows to avoid fill-in.
  2. Choose BDF at relative tolerance 1e-5 and below, Rodas4 above (pick your own switch point by testing).
  3. Output on a fixed grid by interpolating between steps. If a run blows up, retry once with a tighter absolute tolerance.
  4. Check: compare with roadrunner at its own tolerances and with the high-accuracy reference.

Step 5. Rules, events and the rest of SBML

Add assignment and rate rules, then events (watch each comparison in the trigger for a sign change, locate the exact crossing, apply assignments, handle delay and priority), then variable compartments, conversion factors and the other features in section 7. After each feature, run the matching SBML Test Suite cases.

Step 6. Sensitivities, Gillespie and batches

  • Sensitivities: integrate the extra equations dS/dt = J·S + ∂f/∂p with exact derivatives, one parameter per core.
  • Gillespie: pick the next reaction and time from the propensities; seed each run.
  • Batches: run many parameter sets in parallel with rayon; each gets its own copy of the state.

Step 7. Connect it to tellurium

  1. Expose the Rust engine to Python with PyO3 (roadrunner_rs), built with pip install ./rrs.
  2. Write the bridge: read SBML with libsbml and build the Rust model (step 2's tapes plus stoichiometry, rules, events). Compute starting values with your own formula evaluator, including initial assignments.
  3. Subclass tellurium's ExtendedRoadRunner. Route every expensive method through one function that tries Rust and, if Rust raises "can't do this exactly", calls the original roadrunner method. Record what happened.
  4. Make loading lazy: create an empty roadrunner object and only compile the model in roadrunner when a call needs it, passing it the current state.
  5. Check: run tellurium's own test suite with the new engine on and off; the results must be identical.

Step 8. The JIT

For each tape, count uses. After 2,000, translate the tape instruction by instruction into Cranelift's intermediate language, compile it, and call the compiled function from then on. Check: the compiled result must be bit-identical to the tape on random inputs.

Step 9. The hard SBML features

Add delays (state history + Hermite interpolation), comp flattening, fast-reaction rewriting, algebraic rules (eliminate when possible, otherwise diffsol), random draws, and the hybrid SSA (section 7). Then switch on strict mode and run the whole SBML Test Suite with benchmarks/sts/run.py and run_stochastic.py. Fix every failing case until all pass.

Step 10. Publish the numbers

Rerun the benchmarks (benchmarks/run.py, benchmarks/bigmodel/run.py) and both test suites, and report time, cores used, memory and error for every version.

9. How we know the answers are right

  • SBML Test Suite, 1,923 / 1,923 with the backup off. The official suite (sbmlteam/sbml-test-suite, commit bbcbc80). All 1,789 semantic time courses run in Rust and match the expected numbers within each case's own tolerances; all 34 flux-balance cases pass in te.fba; all 100 stochastic cases pass with 10,000 runs each, judged by the suite's own rule ("Z or Y failing 0-1 times per test"). With the suite's standard-deviation test applied strictly, 96 of 100 pass; the other 4 have very skewed distributions, and at up to a million runs their averages and spreads match the expected values. Before this work: 1,405 / 1,789 with the backup on.
  • Tellurium's own tests. The upstream test suite (385 tests) gives identical results with regular tellurium, Turbo and Nitro. Nitro's own suite passes in full: 417 passed, 0 failed, 8 skipped (need internet or optional extras).
  • Side-by-side checks. Every Rust feature has a test that runs the same model through roadrunner and compares (tellurium/tests/test_turbo.py, rrs/check.py, Rust unit tests). The random distributions are checked against their known averages and spreads.
  • Against the truth, not just each other. The benchmark compares all versions with a very-high-accuracy reference, so it shows who is closer to the true answer.
  • Where answers differ, we found out why. Control coefficients differ by about 5e-8 because roadrunner's trial-step slopes are approximate. We also found cases where roadrunner itself is wrong (sensitivities when an event changes a value, uninitialised numbers in getDependentRatesOfChange); Nitro gives the correct values.

Old tellurium bugs fixed along the way

  • SED-ML files that load experimental data (CSV, TSV, NuML) crashed; fixed (13 failing tests).
  • te.executeSEDML("file.omex") crashed with NameError: CombineArchive; fixed.
  • Tiled figures crashed after te.disablePlotting(); fixed.
  • Missing phrasedml silently hid the inline OMEX tools; now it says so.
  • Inline OMEX left a temporary folder behind each run; fixed.
  • distributed_sensitivity_analysis bounds check and run_case(..., py_code=True) fixed; the Python 2 six import removed.

11. What still goes to roadrunner, and known differences

Roadrunner is not loaded at all for normal work. It is loaded once, on demand, for:

  • Editing the model's structure (addReaction and similar) and exporting to CellML / Matlab.
  • Link and conservation matrices, and conservedMoietyAnalysis = True: these must pick the same "independent" chemicals as roadrunner's structural analysis.
  • Integrators other than CVODE and Gillespie (for example Euler or RK4).
  • getFrequencyResponse: there is no trustworthy reference to check a new version against.
  • Second-order sensitivities.
  • Small getters (about 1 µs in C++), where calling into Rust would cost more than it saves.

Known limits: delay() inside a DAE model with algebraic constraints that can't be eliminated is not supported; the hybrid SSA uses fixed tolerances and is slower than the pure SSA on large models.

Known differences, where Nitro is right and roadrunner is not: roadrunner carries sensitivity state into the next call even after reset(); it ignores event changes inside sensitivities; it returns uninitialised values from getDependentRatesOfChange when moiety analysis is on.

JacobianTable of how every rate changes when every amount changes; needed by fast solvers.
ElasticityHow sensitive one reaction's speed is to one chemical's level.
Control coefficient (MCA)How much a whole pathway's output depends on one reaction.
Finite differencesEstimating a slope by trying small steps; slow and approximate.
Symbolic derivativeThe exact slope formula, worked out by algebra.
IntegratorThe method that steps a model forward in time (Rodas4, BDF, CVODE).
ToleranceHow much error the integrator may make per step; smaller = more accurate and slower.
Newton's methodFast way to solve equations by repeatedly following the slope.
Conservation lawA total that never changes (e.g. free + bound enzyme).
DAEDifferential-algebraic equations: some values change over time, others must always satisfy an equation.
Hermite interpolationA smooth way to estimate a value between two saved points, using their slopes too.
Gillespie / SSASimulation of random individual reaction events.
Linear programFinding the best value of a straight-line formula under straight-line limits (used by FBA).
TapeThe engine's compact step-by-step list representing a formula.
JIT (just-in-time compiler)Turns the tape into the processor's native instructions while the program runs.
Cranelift / LLVMCode-generator libraries; Nitro uses Cranelift, roadrunner uses LLVM.
Facade / traffic controllerThe layer that routes each call to Rust or to the original engine.
Strict modete.turbo('strict'): backup off; Rust or an error.
GILPython's lock that lets only one thread run Python code at a time.
libsbmlThe standard library for reading and writing SBML model files.
Lazy loadingNot doing an expensive step (here: compiling the model in roadrunner) until something needs it.
